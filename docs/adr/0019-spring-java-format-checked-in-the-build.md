# ADR-0019: Spring Java Format, checked in the build

- **Status:** Accepted
- **Date:** 2026-11-16

## Context

Nothing checked the formatting of the code. Most of it is written by agents, and each change
brought its own line breaks; a reader of a diff had to tell formatting noise from changes.

The project was generated by Spring Initializr, with tabs, and the code kept that style. Measured
on 2026-11-16 with `spring-javaformat:validate`, 40 of the 59 source files already complied with
Spring Java Format; the other 19 needed line breaks moved.

## Decision

The code is formatted with **Spring Java Format** (`spring-javaformat-maven-plugin` 0.0.48).
Its `validate` goal runs in Maven's `validate` phase, so `./mvnw verify` fails on unformatted
code, in CI as well as locally, and CI needed no change. `./mvnw spring-javaformat:apply` formats.

The formatter has no options. It is the style the Spring team uses for Spring Boot itself, so the
choice comes down to one sentence: a Spring project formatted in Spring's style.

It came in three commits. First the two queries were rewritten as text blocks, which the formatter
leaves untouched, so that it would not join the concatenated SQL into one line. Then the
reformat, alone and with no other change: 17 files. Then the plugin. Each commit builds green.
The reformat commit is listed in `.git-blame-ignore-revs`, so `git blame` and GitHub skip it and
attribute each line to the change that wrote it.

The plugin's version is pinned in the pom because the Spring Boot BOM does not manage it.

## Alternatives considered

- **Spotless with google-java-format or palantir-java-format.** Both indent with spaces (two and
  four), so adopting either rewrites all 59 files instead of 17. Spotless is also a wrapper that
  adds a layer of configuration of its own.
- **Spotless with an Eclipse formatter profile.** Every rule can be tuned, and every rule tuned is
  one more choice to explain. The value of a formatter here is that nobody chooses.
- **Checkstyle alone, or an `.editorconfig`.** Checkstyle reports and does not fix, so every
  violation is a manual edit; an `.editorconfig` is a hint to the editor that CI does not enforce.

## Consequences

- Formatting stops showing up in diffs and in review.
- Hand-made layout is lost where it carried meaning. Ledger tests that listed one order per line,
  like a table, are joined up to 120 columns; the layer definitions in `ArchitectureTest` lose the
  pairing of each `layer` with its `definedBy`. The formatter honours `@formatter:off`, but that is
  a comment, and constitution VII forbids comments. Where the layout matters, the code has to carry
  it: a local variable per order, for instance.
- SQL is written in text blocks from now on: the formatter leaves them as written.
- In IntelliJ, the `spring-javaformat-intellij-idea` plugin formats the same way as the build.
